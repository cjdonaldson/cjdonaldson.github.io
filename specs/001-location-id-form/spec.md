# Feature Specification: Location ID Generation in Location Form

**Created**: 2026-03-20
**Status**: Completed
**Input**: User description: "add location id part 2 — adjust camping/location-form.html to generate the location id when generating the json data."

## Overview

The `camping/location-form.html` form lets a site maintainer describe a campsite/location and export a structured JSON blob for copy-paste into the site's data files. Currently that JSON contains no unique identifier. Part 1 of this work added `id` values to existing location records via a standalone script (`location-id-gen.js`). Part 2 integrates the same ID-generation logic directly into the form so that every newly created JSON record is born with an `id` — no post-processing step required.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Generated JSON Includes id (Priority: P1)

A site maintainer fills out the location form with all required fields — including latitude and longitude — and clicks **Generate JSON**. The resulting JSON blob contains an `id` field whose value is the stable 8-character identifier derived from the entered coordinates. The maintainer can immediately paste the complete JSON into the data file without running any external script.

**Why this priority**: This is the core deliverable. Every other story is secondary to the fundamental behavior of the ID appearing in the output.

**Independent Test**: Open `camping/location-form.html` in a browser, fill in valid latitude and longitude (e.g., `27.1392` / `-82.4526`), fill in the remaining required fields, click **Generate JSON**, and confirm that the output JSON contains `"id": "a1b2c3d4"` (or an equivalent 8-hex-character string consistent with hashing `"27.1392,-82.4526"`).

**Acceptance Scenarios**:

1. **Given** the form is loaded and all required fields are filled with valid data, **When** the user clicks **Generate JSON**, **Then** the JSON output contains an `id` field with an 8-character hexadecimal value.
2. **Given** latitude `27.1392` and longitude `-82.4526` are entered, **When** JSON is generated, **Then** `id` equals the value produced by running `location-id-gen.js "27.1392,-82.4526"`.
3. **Given** the same latitude and longitude are entered on two separate form sessions, **When** JSON is generated each time, **Then** both outputs contain the same `id` value (the ID is stable/deterministic for a given coordinate pair).

---

### User Story 2 - Coordinate Normalization to 4 Decimal Places (Priority: P2)

The ID-generation algorithm requires coordinates expressed to exactly 4 decimal places (e.g., `27.1392,-82.4526`). If a maintainer enters a latitude or longitude with fewer or more decimal places, the form normalizes the values to 4 decimal places before computing the ID, so the result always matches what the standalone script would produce for the same physical location.

**Why this priority**: Without normalization, a maintainer entering `27.14` or `27.13920000` would get a different ID than the canonical 4-decimal form, silently creating an inconsistency with any ID already generated by the standalone script for that location.

**Independent Test**: Open `camping/location-form.html`, enter latitude `27.139` (3 decimal places) and longitude `-82.45` (2 decimal places), generate JSON, then run `node location-id-gen.js "27.1390,-82.4500"` in a terminal and confirm both produce the same `id`.

**Acceptance Scenarios**:

1. **Given** latitude is entered as `27.14` (2 decimal places), **When** JSON is generated, **Then** the ID is computed as if latitude were `27.1400`.
2. **Given** latitude is entered as `27.13920` (5 decimal places), **When** JSON is generated, **Then** the ID is computed from `27.1392` (normalized to exactly 4 decimal places using half-up rounding via `toFixed(4)`, consistent with the standalone script).
3. **Given** latitude and longitude already have exactly 4 decimal places, **When** JSON is generated, **Then** the ID is computed without any change to the values.

---

### User Story 3 - id Field Placement in JSON Output (Priority: P3)

The `id` field appears as the first key in the generated JSON object so it is immediately visible when the maintainer inspects or pastes the output.

**Why this priority**: Placement is a quality-of-life improvement, not a correctness requirement. The data is valid regardless of field order, but leading with the identifier makes the JSON easier to scan and verify at a glance.

**Independent Test**: Open `camping/location-form.html`, generate any valid JSON, and confirm that `"id"` is the first key in the output blob.

**Acceptance Scenarios**:

1. **Given** valid form data is submitted, **When** the JSON is displayed, **Then** `id` is the first property in the JSON object.

---

### Edge Cases

- What happens when latitude or longitude is left blank? The form fields are already `required`; the browser prevents submission and no JSON is generated — no ID computation is attempted.
- What happens if the entered coordinate resolves to the same ID as an existing location? The ID is deterministic by design; the same physical location always produces the same ID. This is expected behavior, not a collision concern for this feature.
- What happens if latitude or longitude is outside valid geographic ranges (e.g., lat > 90)? The form currently accepts any numeric value; this feature does not add coordinate-range validation. The ID will still be generated from whatever value was entered. Range validation is out of scope.
- What happens if `crypto.subtle` is unavailable at runtime (e.g., the file is opened in Chrome over `file://`)? The Generate JSON handler detects the absence of `crypto.subtle` before attempting any computation, displays a clear error message instructing the maintainer to use Firefox or serve the file over HTTP/HTTPS, and produces no JSON output — neither a complete blob nor a partial or ID-less fallback.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The form MUST include an `id` field in the JSON output whenever JSON is generated. The `id` value MUST NOT be rendered as a separate visible UI element (e.g., a read-only input or label); its only appearance is as a key inside the generated JSON blob.
- **FR-002**: The `id` value MUST be derived solely from the latitude and longitude values entered in the form, using the same deterministic algorithm as `location-id-gen.js`, producing an 8-character hexadecimal result.
- **FR-003**: Both latitude and longitude MUST be normalized to exactly 4 decimal places before the coordinate string is assembled for ID derivation, using standard half-up rounding.
- **FR-004**: The `id` field MUST appear as the first key in the generated JSON object.
- **FR-005**: The form MUST continue to function correctly (all existing fields, validation, copy-to-clipboard, reset) after this change — no regressions.
- **FR-006**: The ID-generation logic MUST run entirely within the browser with no external network requests or server-side calls.
- **FR-007**: The form file (`camping/location-form.html`) MUST remain a single self-contained static HTML file with no new external script dependencies introduced.
- **FR-008**: The latitude and longitude values written into the JSON output MUST be the 4-decimal normalized values (i.e., the same normalized values used as input to the `id` computation), not the raw values as entered by the user.
- **FR-009**: The Generate JSON click handler MUST be declared `async`; `SubtleCrypto.digest()` MUST be awaited inline within the handler body. No user-visible state change (spinner, button disabled state, or loading indicator) is required or permitted during the asynchronous computation — the derivation is fast enough to be imperceptible.
- **FR-010**: If `crypto.subtle` is unavailable at runtime (e.g., when the file is opened in Chrome over `file://`), the Generate JSON handler MUST display a clear, human-readable error message informing the maintainer that ID generation is not supported in the current context and that they must use Firefox or serve the file over HTTP/HTTPS. The handler MUST NOT produce any JSON output — neither a complete blob nor a partial or ID-less fallback — when `crypto.subtle` is absent.

### Key Entities

- **Location ID**: A stable, deterministic 8-character hexadecimal string uniquely identifying a geographic location. Derived exclusively from the coordinate pair rounded to 4 decimal places. Identical to the IDs produced by `location-id-gen.js` for the same input.
- **Coordinate String**: The normalized input to the hash function, formatted as `"<lat>,<lng>"` where each value is expressed to exactly 4 decimal places (e.g., `"27.1392,-82.4526"`). These same normalized values are also written into the JSON output for the latitude and longitude fields — the raw entered values are not preserved in the output.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of JSON blobs generated by the form contain an `id` field — no generated JSON is missing the field.
- **SC-002**: For any latitude/longitude pair entered in the form, the `id` in the output matches the value produced by running `location-id-gen.js` with the same coordinates expressed to 4 decimal places — verified by manual cross-check for at least 3 distinct coordinate pairs.
- **SC-003**: All previously working form behaviors (field validation, optional fields, array fields, copy-to-clipboard, form reset) continue to work correctly after the change — confirmed by a full manual walkthrough with no regressions.
- **SC-004**: The `camping/location-form.html` file is fully functional when opened in Firefox directly from the local filesystem (`file://`) or when served over HTTP/HTTPS in any modern browser. Chrome over `file://` is **not** a supported context — `crypto.subtle` is unavailable there, and the form MUST display a clear error message and block JSON generation rather than silently producing broken or ID-less output. File size increases by no more than 2 KB over the current baseline.

## Assumptions

- The browser's built-in `crypto.subtle` API is available when the form is opened in Firefox (any origin, including `file://`) or in any modern browser served over HTTP/HTTPS. Chrome restricts `crypto.subtle` to secure contexts; opening the file in Chrome over `file://` will render `crypto.subtle` unavailable. No polyfill is used; the form detects the absence of `crypto.subtle` at runtime and surfaces a clear error, blocking JSON generation.
- Coordinates entered by the maintainer represent real-world locations and will always have a numeric value when the form is submitted (the existing `required` attribute on the latitude and longitude fields enforces this).
- Standard half-up rounding to 4 decimal places is the correct normalization to apply, consistent with how the standalone `location-id-gen.js` script is used in practice.
- No UI indicator (spinner, disabled state) is needed during ID computation; the derivation is fast enough to be imperceptible to the user. The handler is implemented as an `async` function that `await`s `SubtleCrypto.digest()` inline.
